# Сценарий: недоставленное SMS

**Идентификатор для JSON поля `scenario`:** `sms_delivery`

**Слоты (`slots`):** для шага с запросом к `send_sms` обязателен ключ `phone` (строка — абонентский номер, как вы определили из текста; не цифры из почты или версии приложения).

**Подстановка в SQL:** в рекомендованном запросе оставляй плейсхолдер `{{phone10}}` без изменений — исполнитель подставит нормализованный национальный номер (10 цифр после ведущей 7/8) из `slots.phone`.

Когда пользователь спрашивает, почему клиенту не пришло SMS, без дополнительных деталей, действуй по шагам:

1. Определи абонентский номер из сообщения пользователя.
   - Если номер не удаётся определить надёжно — `next`: `finish`, `scenario`: `sms_delivery`, `slots`: `{}`, в `task`/`reason` попроси номер в формате `8XXXXXXXXXX`.

2. Если номер есть и нужны факты из БД — `next`: `db`, `scenario`: `sms_delivery`, `slots`: `{"phone":"<определённый номер>"}`.
   - Сформируй `task`: запрос в таблицу `send_sms` по этому номеру, последние 5 записей, сортировка по времени (см. SQL ниже).

3. В результате запроса нужны поля:
   - `phone_number` — номер телефона, исходное значение из БД
   - `received_date` — дата поступления SMS в очередь отправки
   - `sending_date` — дата фактической отправки
   - `sms_text` — текст SMS
   - `result` — результат отправки
   - `operator_type` / `operator_name` — оператор связи
   - `error_text` — текст ошибки, если отправка завершилась ошибкой

4. Рекомендованный SQL (вставь в `task` как блок ```sql ... ```):
   - `SELECT
    ss.phone_number,
    ss.received_date,
    ss.sending_date,
    ss.sms_text,
    ss.result,
    ss.error_text,
    oa.sender_name,
    op.type AS operator_type,
    op.name AS operator_name,
    regexp_replace(ss.phone_number, '[^0-9]', '', 'g') AS normalized
    FROM send_sms ss
    LEFT JOIN operator_accounts oa ON ss.account_id = oa.id
    LEFT JOIN operators op ON op.id = oa.operator_id
    WHERE regexp_replace(ss.phone_number, '[^0-9]', '', 'g') LIKE '%{{phone10}}'
    ORDER BY COALESCE(ss.sending_date, ss.received_date) DESC
    LIMIT 5;`

5. Ограничение доступа MCP:
   - Только запросы на чтение (SELECT / WITH / EXPLAIN, без изменения данных).
   - Любые `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `DROP`, `ALTER`, `CREATE` запрещены.

6. Если записей нет — в финальном ответе явно скажи, что отправки по номеру не найдены.

7. Если записи есть — краткий вывод по причине недоставки и перечисление найденных записей.

---

### План на будущее: сначала `users.isActive` в другой БД

Когда появится второй источник (другая БД), опишите **отдельный шаг** в этом файле: свой SQL, какие `slots` нужны (например тот же `phone` или `user_id`), и ожидаемое поле `isActive`. В коде оркестратора понадобится **несколько шагов** (цикл или граф): сначала запрос к нужному DSN/алиасу, результат в состоянии, затем при успехе — шаг `send_sms`. Один вызов `db` с двумя SQL в одной строке в разные БД без доработки исполнителя обычно не делают — разделяйте шаги и целевые `targets` в конфиге.
